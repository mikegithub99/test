# Java gRPC Client — Design and Usage\n\nThis document describes the Java 21 / Spring Boot side of the gRPC service-discovery architecture.\n\n# Section 1 — Java Client\n\n## 1.1 Architecture\n\n```text\nSpring Boot application\n        |\n        v\n    CustomerApi\n        |\n        v\n   JDK failover proxy\n        |\n        v\n  GrpcClientManager\n        |\n        +------------------------+\n        |                        |\n        v                        v\n ServiceDiscovery          cached GrpcClient\n        |                        |\n   +----+-----+                  +-- ManagedChannel\n   |          |                  |\n Registry    Static              +-- CustomerGrpcClient\n   |          |                         |\n   +----+-----+                         +-- generated gRPC stub\n        |\n        v\n  service instance\n```\n\n- **ServiceDiscovery** determines where an instance of a logical service is located.\n- **GrpcClientManager** owns active clients, channels, caching, replacement, failover, and lifecycle.\n- **GrpcClientFactory<T>** is the only generic infrastructure abstraction. It creates a service-specific client from a `ManagedChannel`.\n- **CustomerGrpcClient** knows the generated `CustomerServiceGrpc` stub and implements `CustomerApi`.\n- The **JDK proxy** exposes the application-facing `CustomerApi`.\n\nThe manager is deliberately **not generic**. There is no `GrpcClientManager<CustomerApi>`.\n\n## 1.2 Application API and gRPC adapter\n\n```java\npublic interface CustomerApi {\n    String getCustomer(String customerId);\n}\n```\n\n```java\npublic final class CustomerGrpcClient implements CustomerApi {\n\n    private final CustomerServiceGrpc.CustomerServiceBlockingStub stub;\n\n    public CustomerGrpcClient(ManagedChannel channel) {\n        this.stub = CustomerServiceGrpc.newBlockingStub(channel);\n    }\n\n    @Override\n    public String getCustomer(String customerId) {\n        return stub.getCustomer(\n                GetCustomerRequest.newBuilder()\n                        .setCustomerId(customerId)\n                        .build()\n        ).getName();\n    }\n}\n```\n\nThe adapter knows the protobuf-generated Java type. The generic discovery and channel-management infrastructure does not.\n\n## 1.3 Static discovery and Spring beans\n\nStatic discovery describes **logical service names and service instances**. It does not map a Java protobuf type to a host.\n\n```yaml\ngrpc:\n  discovery:\n    mode: STATIC\n    services:\n      CUSTOMER_SERVICE:\n        - instance-id: customer-1\n          host: server-a\n          port: 50051\n        - instance-id: customer-2\n          host: server-b\n          port: 50051\n        - instance-id: customer-3\n          host: server-a\n          port: 50052\n```\n\nThe configuration means:\n\n```text\nCUSTOMER_SERVICE -> customer-1 -> server-a:50051\nCUSTOMER_SERVICE -> customer-2 -> server-b:50051\nCUSTOMER_SERVICE -> customer-3 -> server-a:50052\n```\n\nIt does not mean `CustomerServiceGrpc -> server-a:50051`.\n\n### Complete Spring `@Bean ServiceDiscovery` example\n\n```java\n@Configuration\npublic class GrpcDiscoveryConfiguration {\n\n    @Bean\n    ServiceDiscovery serviceDiscovery() {\n        Map<String, List<ServiceTarget>> services = Map.of(\n                "CUSTOMER_SERVICE",\n                List.of(\n                        new ServiceTarget(\n                                "CUSTOMER_SERVICE",\n                                "customer-1",\n                                "server-a:50051"),\n                        new ServiceTarget(\n                                "CUSTOMER_SERVICE",\n                                "customer-2",\n                                "server-b:50051"),\n                        new ServiceTarget(\n                                "CUSTOMER_SERVICE",\n                                "customer-3",\n                                "server-a:50052")\n                )\n        );\n\n        return new StaticServiceDiscovery(services);\n    }\n\n    @Bean(destroyMethod = "close")\n    GrpcClientManager grpcClientManager(ServiceDiscovery serviceDiscovery) {\n        return new GrpcClientManager(serviceDiscovery, 100);\n    }\n}\n```\n\nThe important bean is explicitly:\n\n```java\n@Bean\nServiceDiscovery serviceDiscovery() {\n    return new StaticServiceDiscovery(services);\n}\n```\n\nSpring injects that `ServiceDiscovery` implementation into the manager. In a real application, the map would normally be populated from YAML properties.\n\n## 1.4 Registry discovery\n\nThe same manager can use the external registry:\n\n```yaml\ngrpc:\n  discovery:\n    mode: REGISTRY\n    registry:\n      host: registry-host\n      port: 9090\n```\n\nOnly the `ServiceDiscovery` implementation changes; the application API, proxy, manager, factory, and channel lifecycle remain the same.\n\n## 1.5 Why only the factory is generic\n\n```java\n@FunctionalInterface\npublic interface GrpcClientFactory<T> {\n    T create(ManagedChannel channel);\n}\n```\n\n`CustomerGrpcClient::new` is equivalent to `channel -> new CustomerGrpcClient(channel)`.\n\nThe manager discovers a `ServiceTarget`, creates the `ManagedChannel`, then passes that channel to the factory. The factory is therefore the boundary where the generic infrastructure hands the transport to the service-specific adapter.\n\n## 1.6 CustomerApi proxy\n\n```java\n@Bean\nCustomerApi customerApi(GrpcClientManager manager) {\n    InvocationHandler handler = (proxy, method, args) ->\n            manager.execute(\n                    "CUSTOMER_SERVICE",\n                    CustomerGrpcClient::new,\n                    client -> method.invoke(client, args)\n            );\n\n    return (CustomerApi) Proxy.newProxyInstance(\n            CustomerApi.class.getClassLoader(),\n            new Class<?>[]{CustomerApi.class},\n            handler\n    );\n}\n```\n\nApplication code continues to call `customerApi.getCustomer("123")` without knowing which server instance or channel is currently active.\n\n## 1.7 Channel semantics\n\nA `ManagedChannel` is the reusable client-side transport used by the generated gRPC stub. A particular `CustomerGrpcClient` is constructed around the channel supplied to its constructor.\n\nThe current manager maintains **one active `GrpcClient` and channel per logical service name**:\n\n```text\nCUSTOMER_SERVICE -> active client -> channel -> discovered instance\nORDER_SERVICE    -> active client -> channel -> discovered instance\n```\n\nThe channel is **not keyed by Java type**.\n\nIf customer and order both resolve to `server-a:50051`, the current design still has separate channels:\n\n```text\nCustomerGrpcClient -> server-a:50051 -> ManagedChannel #1\nOrderGrpcClient    -> server-a:50051 -> ManagedChannel #2\n```\n\nChannel sharing is intentionally not inferred from matching endpoints. It can be introduced later as an explicit transport optimization.\n\n## 1.8 Initial call — channel creation walkthrough\n\nAssume discovery returns `customer-1 -> server-a:50051` on the first lookup.\n\n```text\nCustomerApi.getCustomer("123")\n        |\n        v\nJDK proxy\n        |\n        v\nGrpcClientManager.execute(...)\n        |\n        v\nServiceDiscovery.lookup(...)\n        |\n        v\ncustomer-1 -> server-a:50051\n        |\n        v\nManagedChannel #1\n        |\n        v\nCustomerGrpcClient::new(channel1)\n        |\n        v\ngenerated CustomerServiceBlockingStub\n        |\n        v\nRPC\n```\n\nThe manager caches that client/channel pair. Future calls reuse it rather than creating a new channel for every RPC.\n\n## 1.9 Retryable exception — replacement channel walkthrough\n\nSuppose `customer-1` becomes unavailable and the RPC returns `UNAVAILABLE`.\n\n1. The manager detects the configured retryable gRPC status.\n2. It removes the active client for `CUSTOMER_SERVICE`.\n3. The cache entry is invalidated.\n4. The old client is retired and its `ManagedChannel #1` is shut down.\n5. Discovery is called again with `customer-1` excluded.\n6. Suppose discovery returns `customer-2 -> server-b:50051`.\n7. The manager creates `ManagedChannel #2`.\n8. It invokes `CustomerGrpcClient::new(channel2)`.\n9. The generated stub is therefore attached to channel #2.\n10. The original operation is retried using the replacement client.\n\n```text\nOLD\nCustomerGrpcClient #1\n        |\nManagedChannel #1\n        |\ncustomer-1\n        |\nUNAVAILABLE\n        |\n        v\nremove + invalidate + retire\n        |\n        v\nfresh lookup excluding customer-1\n        |\n        v\nNEW\nManagedChannel #2\n        |\nCustomerGrpcClient #2\n        |\ncustomer-2\n        |\nretry original operation\n```\n\nThe application-facing `CustomerApi` proxy does not change. Only the cached service-client/channel pair underneath it changes.\n\n## 1.10 Multiple channels to the same logical service\n\nThe initial design intentionally has one active channel for a logical service:\n\n```text\nCUSTOMER_SERVICE -> one active client -> one active channel -> one instance\n```\n\nA future channel pool could instead maintain:\n\n```text\nCUSTOMER_SERVICE\n       |\n   channel pool\n   /    |    \\n #1    #2    #3\n |     |     |\n A     B     C\n```\n\n**Pros:** higher concurrency when one HTTP/2 connection becomes a bottleneck, isolation for heavy workloads, and deliberate distribution across multiple connections.\n\n**Cons:** more TCP/HTTP/2 connections, more connection and keepalive overhead, more memory, and more complex lifecycle, failover, metrics, and channel-selection logic.\n\nFor the initial implementation, one channel per logical service is intentionally simpler. If load testing later demonstrates a need for multiple channels, introduce an explicit `GrpcChannelPool` rather than making `GrpcClientManager<T>` generic.\n\n## 1.11 Channel sharing across service types\n\nTwo service adapters could theoretically share one channel:\n\n```text\nserver-a:50051\n       |\nManagedChannel\n    /      \\nCustomer   Order\n adapter   adapter\n```\n\nThat can reduce connections and improve transport reuse, but it requires explicit ownership rules so one service cannot retire a channel still used by another. The current implementation therefore keeps channel ownership separate.\n\n## 1.12 Adding another service\n\n```java\npublic interface OrderApi {\n    Order getOrder(String orderId);\n}\n```\n\n```java\npublic final class OrderGrpcClient implements OrderApi {\n    private final OrderServiceGrpc.OrderServiceBlockingStub stub;\n\n    public OrderGrpcClient(ManagedChannel channel) {\n        this.stub = OrderServiceGrpc.newBlockingStub(channel);\n    }\n}\n```\n\nUsage:\n\n```java\nmanager.execute(\n        "ORDER_SERVICE",\n        OrderGrpcClient::new,\n        client -> client.getOrder("12345")\n);\n```\n\nStill no `GrpcClientManager<OrderApi>`.\n\n## 1.13 Lifecycle and shutdown\n\nThe manager owns cached client and channel lifecycle. A channel should not be shut down merely because one RPC failed; other application threads may still be using it.\n\nRetirement occurs when the manager/cache replaces or evicts the client, or when the manager closes during application shutdown.\n\n```java\n@Bean(destroyMethod = "close")\nGrpcClientManager grpcClientManager(ServiceDiscovery serviceDiscovery) {\n    return new GrpcClientManager(serviceDiscovery, 100);\n}\n```\n\n## 1.14 Kubernetes migration\n\nThe application-facing design can remain unchanged when discovery moves from the interim registry to Kubernetes.\n\n```text\nGrpcClientManager\n       |\n       v\nServiceDiscovery\n    /        \\nStatic      Registry\n                |\n             future\n                |\n           Kubernetes\n```\n\nOnly the discovery implementation needs to change. The application API, service-specific adapter, manager, channel lifecycle, and retry structure remain independent of the discovery source.\n\n# Java Design Summary\n\nThe Java type does **not** determine the channel.\n\nThe logical service name determines what discovery looks up.\n\nThe discovered target determines where the channel connects.\n\nThe generic factory determines which service-specific adapter is constructed on that channel.\n\nOn a retryable failure, the manager can replace the client/channel pair while keeping the application-facing `CustomerApi` stable.
